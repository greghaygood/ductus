# `ductus`

The `ductus` framework — a pipeline-driven spec-to-implementation flow scaffolded into adopted projects.

> **Agents:** this file is the committed home for project rules — append durable learnings to the matching section (Gotchas, Workflow, Boundaries, Code Style, Testing). Add a new section only when none fits.

## Constitution

See [constitution.md](framework/constitution.md) — guiding principles, development pipeline, spec lifecycle, and quality standards that govern this project.

## Project Structure

The `framework/` directory is ductus's source — everything that ships to adopted projects via `/ductus`. It is laid out by IA primary purpose, not by file kind:

- `framework/constitution.md` — the constitution shipped to adopted projects (lands at `.ductus/constitution.md` in adopter repos)
- `framework/rules/` — domain rule sets adopted projects can reference (security-backend, security-frontend, …)
- `framework/templates/spec/` — templates consumed by an agent during the pipeline (spec, plan, tasks, data-model, research, scenario)
- `framework/templates/project/` — project document templates consumed once at adoption (agents, claude-md, system, errors, events, project-readme, gitignore, inbox)
- `framework/commands/` — operational slash command sources only
- `framework/bootstrap/` — the `ductus.md` installer plus per-agent permission files at `bootstrap/configure/{key}.md`

When adding files under `framework/`, place them by purpose, not by extension.

## Tech Stack

`ductus` is a text-first framework. The implementation is intentionally narrow:

- **Markdown** — every primary artifact (constitution, specs, plans, tasks, scenarios, rules, slash command sources, templates) is plain markdown; markdown is the source-of-truth *format* per [§text-first-artifacts](framework/constitution.md#text-first-artifacts). Format is not durability: `spec.md`, scenarios, and rules are durable sources of truth (with `plan.md` / `data-model.md` as design records), while `tasks.md` is ephemeral work-tracking — see [§tasks-phase](framework/constitution.md#tasks-phase).
- **Bash scripts** under `scripts/` — generators (`gen-*.sh`), the pre-commit hook installer (`install-hooks.sh`), and lints (`lint-*.sh`). All deterministic; no application logic.
- **GitHub Actions YAML** under `.github/workflows/` — CI configuration only.
- **Node.js / `markdownlint-cli2`** — invoked at lint time only; not a build dependency and never published. Declared in `package.json` and pinned by `package-lock.json` so the requirement is discoverable and the version is recorded — bare `npx markdownlint-cli2` resolves whatever is latest that day, so contributors and CI could disagree with nothing saying which version was meant. `npm ci` installs it; `node_modules/` is gitignored. Either invocation works once Node is on `PATH`, and the runtime's `lint-markdown` primitive prefers the local `node_modules/.bin/markdownlint-cli2` when present. **Node must be resolvable by spawned processes, not just by your shell** — under a lazy-loading nvm setup `node` and `npx` are shell functions that a child process never inherits, so the MCP server, the pre-commit hook's `cargo test`, and `check-review-gate` all fail with `could not launch npx` while your own terminal works fine. Put the real Node `bin` directory on `PATH`.
- **Rust** under `runtime/` — the `ductus` deterministic runtime (spec 022), a bin + lib crate on edition 2024 with an MSRV of `1.88`, using `rmcp` as the MCP SDK. It executes the mechanical half of every pipeline command (parsing frontmatter and markdown structure, walking tasks, atomic writes, gate handshakes) and exposes each capability as an MCP tool per [§runtime-boundary](framework/constitution.md#runtime-boundary) principle 5. It never calls an LLM — semantic judgment stays in the slash commands (principle 2).

The runtime is **required, and acquired by the pipeline** ([§runtime-boundary](framework/constitution.md#runtime-boundary) principle 3): `/ductus` downloads the pinned release asset into a ductus-owned store during adoption, so acquisition failure halts the run rather than degrading to a second execution path. It ships in lockstep with the framework — see the release entry under §Workflow for the three version sites and the `ductus-v<version>` tag that actually delivers a `runtime/` change. Binaries are published for five targets; `PATH` is never consulted. There is still no database and no long-running service, and [§runtime-boundary](framework/constitution.md#runtime-boundary) ("What the runtime is not") forbids adding one without a constitutional amendment.

When further tooling-language decisions arise (a second binary the framework might ship), prefer Rust, as the runtime already does. The recent generation of Rust CLI tooling (`ripgrep`, `fd`, `bat`, `eza`, `helix`, `tokei`, `hyperfine`, etc.) has set the modern baseline for CLI UX patterns (single static binary, fast cold-start, sensible exit codes). Go is the credible alternative if development velocity matters more than production characteristics; other languages typically don't fit (distribution complexity, startup overhead, ecosystem fit).

## Workflow

- **Commit directly to `main` — this repo uses trunk-based development.** `ductus` is live-on-main: the installer and everything `/ductus` fetches track `main`, so there is no release branch and no feature-branch/PR step. When the user asks to land work, commit to `main` and push — do **not** branch first (the general "branch off the default branch before committing" default does not apply here). Reason: confirmed by the user 2026-06-11 after a `fix(003)` bootstrap fix was committed straight to `main`, and **again on 2026-08-31**, when an agent branched for spec 054 anyway. The cause is worth stating exactly, because it is not that this file is too long. The agent read it with a shell command whose output exceeded the tool's cap; the harness saved the full text to a temp file and returned only the first 2KB as a preview, with an explicit notice saying so. The agent used the preview and never opened the saved file, so it never reached line 40 and fell back to its generic branch-first default. **Two lessons, and the first is the one that generalises: a truncation notice is not a read — follow the pointer or re-read in ranges.** The second is that a rule which only works when a 90KB file is read in full is a diligence dependency, so this one is now restated in `CLAUDE.md` §Non-negotiables, which is small and always loaded whole. How to apply: branch only when the user explicitly asks, or for a risky spike they want isolated; otherwise small commits reviewed in place on `main` are the norm, matching the existing history.
- **Never create a repository named `govern` under this account again, and never reuse a retired project name.** [049](specs/049-rename-govern-to-ductus/spec.md) renamed the project, and GitHub's rename redirect — which is what keeps every adopter's bootstrap fetch working until they next run it — holds *only for as long as the old name is not reused*. Recreating it silently severs that redirect for every adopter who has not yet re-bootstrapped: no error on this side, no signal, and the failure appears only in their next run. Reason: confirmed against GitHub's rename documentation while resolving 049; it is the one failure mode in that rename with no detection. How to apply: treat the retired name as permanently burned. The same reasoning applies to the retired crates.io crate, which is left published-and-deprecated rather than yanked so existing installs keep resolving.
- **A `runtime/` change ships via a `ductus-v<version>` tag — the commit alone reaches nobody.** The runtime is released (cross-compiled binaries + crates.io publish) by `.github/workflows/runtime-release.yml`, which triggers *only* on a pushed `ductus-v*` tag. So a change under `runtime/` is not "landed" until you: (1) bump **all three** of the repo-root `version` file, `runtime/Cargo.toml` `version`, and a matching `runtime/CHANGELOG.md` section, in one commit (tag scheme `ductus-v<MAJOR>.<MINOR>.<PATCH>`, a runtime bug fix is a patch bump) — `/audit` Family 20 fails when they disagree, and `/ductus` reads the `version` file to decide which runtime to acquire, so a stale pin sends every adopter after assets that do not exist. **The commit is what breaks them, not the tag's absence later** — `/ductus` fetches the pin live from `raw.githubusercontent.com/stonean/ductus/main/version` in pre-flight, so the moment a version bump lands on `main` every adopter whose store is not already that version fetches `releases/download/ductus-v<pin>/…`, gets a 404, and §Runtime acquisition → Failure **aborts the run** rather than degrading. It hits State A and State B alike; only a project setting `[runtime] path` survives, by taking Branch 1 and warning. **Nothing gates this**: Family 20 compares the three version sites to each other, not to what is published, and the audit is green throughout. Surfaced 2026-09-13 — `2266ed4` bumped the pin to 0.49.1 and deferred the tag on the recorded grounds that "no adopter is blocked," which was true of the change's content and false of acquisition; adopters were halted for about four and a half hours. So bump and tag in the same sitting, or do not bump: an unreleased pin on `main` is not a deferred release, it is an outage; (2) commit to `main` and push; (3) `git tag ductus-v<version>` at that commit and `git push` the tag. The tag pipeline runs the framework self-audit (`scripts/audit/run-all.sh`) as a **hard release gate** — any finding aborts the publish, the asset upload, and the SBOM — so run it locally *before* tagging. **A local pass is weaker evidence than it looks:** `ductus-v0.28.0`'s first attempt was green locally and failed in CI, because Family 7 used a GNU awk extension that BSD awk (every macOS machine) rejects, and the family exited 0 rather than reporting it could not run. See the Design Principles entry on checks that cannot run — that failure mode hit four different surfaces in that one release. The parity goldens store the version as a `{{runtime-version}}` placeholder (`runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time), so a version bump needs **no golden re-bless**; do not `BLESS=1` for a version change (it would hardcode the literal version and destroy the placeholder). If parity fails on the version line after a bump, the cause is a stale `runtime/target/release/ductus` — `cargo build --release` to refresh it, don't touch the goldens. Reason: surfaced 2026-06-30 — an `apply-manifest` exec-bit fix committed to `main` would have shipped to no adopter without the tag. How to apply: bump + CHANGELOG + commit + `ductus-v<version>` tag + push tag, in that order; never bless goldens to absorb a version delta. **Every affected spec is `done` before the tag is cut — that is the expected state at tag time** (operator decision, 2026-08-28). A release is cut from completed work: each spec's tasks and acceptance criteria are checked, its review is current and non-blocking, and its status reads `done`; only then is the version bumped and the tag pushed. This entry previously said the reverse — that a spec is *not* complete until its tag ships, so `done` came after — which made the two conditions circular and left releases being cut over specs still in flight. The concern that produced the older wording stands and is unchanged: a spec must never sit at `done` with its runtime work unreleased. 042 reached `done` on 2026-07-22 with its `introduced_in = 0.22.0` work untagged, so no adopter could receive the migration and a stale local server binary kept writing legacy paths. Read it as a promise rather than an ordering: closing a spec commits you to tagging in the same session, not later.
- **A pushed tag is not a published release, and `release not found` is the *normal* answer for the ~11 minutes in between.** `.github/workflows/runtime-release.yml` runs seven jobs in order — `audit` → `build` (×5 targets) → `acquire` (×5) → `sbom` → `publish` (crates.io) → `release-assets` → `verify-published` — and the GitHub release is created by **`release-assets`, second from last**, gated on the crates.io publish ahead of it. So `gh release view ductus-v<version>` answers `release not found` for almost the whole run, and that answer on its own says nothing about whether anything is wrong. **Two things make the mid-flight state read like a failure.** The `Acquire <target>` jobs go green early and look like proof the assets are published — they are not: they `download-artifact` the *staged* tarballs from the `build` jobs, so they verify what is about to ship rather than what shipped. The job that tests the real thing is `verify-published` ("Verify the published release is acquirable"), which `needs: release-assets` and runs last. And the outage the entry above records is real, so a not-found is easy to read as that outage when it is only a run in flight. **Read the run before concluding anything**: `gh run view <id> --json status,conclusion` separates `in_progress` from a failed gate in one call, and `--json jobs` names the job still running. **Never delete-and-re-tag a run that is still in progress.** `scripts/lint-release-ordering.sh` forces the crates.io publish *ahead* of the asset upload precisely because that half is irreversible — a version published to crates.io can never be republished — so a premature "recovery" against a run that was about to succeed burns the version number and needs a patch bump rather than a retry. Reason: surfaced 2026-09-13 verifying `ductus-v0.49.1`. The inbox chore enumerated two outcomes — assets present ⇒ done, `release not found` *or* a failed run ⇒ adopter-halting outage — and the true state was a third the list did not name: in flight and on track, with the audit gate and all five builds already green. How to apply: when a release is unconfirmed, check the **run** first and the release second; treat not-found plus `in_progress` as *wait*, and only a `conclusion` of `failure` as the outage.
- **`done` is not the same as *discharged* — the pre-`done` gate and the release audit are both blind to an obligation recorded in prose.** `check-review-gate` reads nine things, in order: whether the spec is already `done`, the feature directory's markdown lint, unresolved scenario open questions, an undischarged `folds-into:`, an undischarged `cross-spec-impact:`, the `review:` block, whether that review is still current, the `analyze:` block, and whether that analysis is still current. It reads nothing else, and `scripts/audit/run-all.sh` never reads `specs/inbox.md` at all. So an obligation recorded anywhere *other* than the `cross-spec-impact:` key — a spec body, a hand-off note, the inbox — passes every gate this project has, while looking exactly like work that was finished. Reason: surfaced 2026-09-11 closing [055](specs/055-shared-constitution/spec.md), which owed [050](specs/050-constitution/spec.md) a cross-spec update under [§cross-spec-impact](framework/constitution.md#cross-spec-impact). It was identified early and written into 055's body as prose, then moved to `specs/inbox.md` when that section was retired at the completion gate — and 055 passed its review, its analysis, the pre-`done` gate and the release audit with the obligation outstanding, so `ductus-v0.47.0` was published before the operator caught it. `diff-cross-spec` reported `cross-spec-paths: []` at that gate, which was true and worthless: it detects the sibling spec you *changed*, never the one you *owe*. The same blindness hid the backlog: at the time nothing reported inbox depth at all, and the two surfaces that showed it were scoped to the current feature's window, so an item older than the feature in hand was invisible by construction. Six items stood in the inbox while that tag was cut. How to apply: before proposing a `done` transition or cutting a tag, read `specs/inbox.md` directly and re-read the spec body for obligations it names — a green gate is evidence about the nine checks above and nothing more. **All three scenarios that closed these gaps have since shipped**, which narrows this entry rather than retiring it. [`the-cross-spec-impact-gate`](specs/022-deterministic-runtime/scenarios/the-cross-spec-impact-gate.md) put the `cross-spec-impact:` check into the gate, keyed on the **reciprocal back-link** rather than on the key's removal, so deleting the key to unblock yourself enforces nothing (`check_review_gate.rs`'s `a_declared_impact_blocks_while_the_target_does_not_link_back` and `an_undischarged_impact_outranks_a_missing_review`). [`the-inbox-row`](specs/022-deterministic-runtime/scenarios/the-inbox-row.md) made `/{project}:implement` and `/{project}:review` render the standing count on **every** run including a clean one, in four distinct states, from `diff-cross-spec`'s `inbox-standing`. The rule half is [`a-declared-cross-spec-impact-gates-done`](specs/050-constitution/scenarios/a-declared-cross-spec-impact-gates-done.md) under 050. **What stays contributor discipline is the part no check can reach:** nothing detects an impact that was never *declared* — [§cross-spec-impact](framework/constitution.md#cross-spec-impact) says so in as many words rather than implying a mechanism it does not have — the standing row is a notice and never a gate, and `dashboard`, `/{project}:status`, `check-review-gate` and the 37 audit families still report no inbox depth. Corrected 2026-09-13: this entry had claimed all three were unbuilt for as long as they had in fact been shipped, which is the stale-prose-claim failure it sits three entries away from.
- **A spec does not reach `done` with an outstanding SHOULD — every review finding is resolved or waived first, not only the MUST ones.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: confirmed by the user 2026-08-16 while closing 010, after I presented a non-blocking `QUAL-CLAIM-001` SHOULD as compatible with the transition; the user noted the rule had been given before, which is the tell that a session-scoped acknowledgement is not enough. How to apply: read `should-violations` at the completion gate the same way you read `must-violations` — non-zero means not done. Fix it, or waive it with a recorded reason and re-run `/{project}:review` so `review.md` and the frontmatter agree; only then propose the transition. When the fix lands under `runtime/`, the release entry above applies in full — the version bump and `ductus-v<version>` tag are part of the same completion gate, so addressing a SHOULD can mean cutting a release. Carry this rule into any hand-off prompt you write: it is a standing project rule, not a preference for one review.
- **Work a recommendation out to its result *before* presenting it.** The rule is [§recommendations](framework/constitution.md#recommendations) — it ships to adopters, so this entry is the contributor-side mirror, not a second copy. Reason: surfaced 2026-08-17 on 048 task 13. Three options were offered for moving the bootstrap's State-B abort, and I recommended the middle one as "the largest gain available"; only after the user accepted did I count the restarts and find it saved **none** — it relocated the abort without removing it, leaving the pre-042 adopter at three sessions, the exact number the scenario exists to reduce. The user had to be told their approval rested on my framing rather than on the facts. The same session then produced the counter-example the rule wants: the acceptance-criterion-supersession check was measured before being recommended (455 pairs tested, 215 would fire, every sample a false positive), and the measurement is what killed it. How to apply here: state the metric the decision turns on, evaluate every option against it, then rank — and when the metric cannot be computed yet, say so and name what would settle it instead of ranking anyway.
- **Never record anything durable in `review.md` — it is regenerated wholesale.** `write-review` rewrites the file on every run, so a note left there is destroyed by the next `/{project}:review`. Anything that must survive belongs in the spec body, on the artifact it describes. Reason: surfaced 2026-08-17 closing 010, whose AC7/AC8 (the `[simple]` marker, dropped by 017) and AC14 (`framework/workflows/`, sunset by 043) all describe things the repo no longer has; the only record of the 017 removal lived in `review.md`'s Summary and was destroyed an hour later by a re-run. How to apply: the detection already works — `/{project}:implement`'s criterion-verification step is what surfaced all three, by checking criteria against the tree rather than against the review.
- **Record a review's `reviewed-against` as a commit that already contains the artifacts it reviewed — so commit the work first, then review, then commit the review.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-17 — 000's review was recorded at `11ff132d`, its scenarios committed in `ccdd3ac`, the local audit ran green before the commit, and the `ductus-v0.29.7` release gate then failed on the audit and skipped the publish. How to apply: two commits, always — the artifact commit, then `/{project}:review` against that new HEAD, then the review commit. And **run `scripts/audit/run-all.sh` after committing, before tagging**; a green pre-commit audit is not evidence for any family that reads history. This is the same lesson as the `fetch-depth: 0` entry one layer up: a check that reads git history answers about committed state, so it must be *asked* about committed state.
- **A review is the five passes, not the `write-review` call — never record findings you did not derive by reading the resolved scope.** `write-review` takes `findings` as an argument and records no denominator, so a review that read none of its scope and one that read all of it produce **byte-identical** records: same counts, same `reviewed-digest`, same `blocking: false`. Neither the primitive nor `check-review-gate`, Family 19, or Family 31 can tell them apart. Contrast `write-analysis`, which requires `unexamined` precisely so a clean analyze cannot be recorded without stating what it could not reach — `analyze.md` argues that case in full and the reasoning was never carried across to the review half. Reason: surfaced 2026-09-12. `/ductus:review` was "run" against 017 and 048 by calling `compute-review-scope`, `process-waivers` and `write-review` directly — skipping `discover-rule-files` and all five passes — and recording `0/0/0` under a Summary reading *"Reviewed … across all five dimensions"*. Both records were false. Re-running the review properly over the same scope found **fifteen** defects, three of them `QUAL-CLAIM-001` violations in shipped adopter CI, including a review-blocking gate that enumerated nothing on a configured spec root and exited 0. The operator caught it from how fast it returned, not from any artifact. How to apply: steps 3–7 of `framework/commands/review.md` **are** the command; `write-review` is how a result is recorded, not how it is produced. Load the rule files, read the in-scope files, derive every count from what you read. The Summary is a claim about work performed and is held to [§grounding](framework/constitution.md#grounding) like any other claim. When the scope is too large to read in one pass, say what was examined and what was not — in the Summary, where the next reader meets it — which is the disposition [§design-principles](framework/constitution.md#design-principles) already prescribes for residue.
- **`examined` counts the in-scope files the passes *read*. A file you are confident about by other means is named in the Summary, never folded into the numerator.** The temptation is specific and recurring: a scope file that is a **generated mirror** of a file you did read, where re-reading it would show you the same bytes with placeholders substituted. Believing it correct and having read it are different claims, and `examined` is only the second — the field exists precisely so a review cannot conflate confidence with coverage. Reason: surfaced 2026-09-13 backfilling [014](specs/014-reclarify-backedge/spec.md), whose 11-file scope included the three generated `.claude/commands/ductus/{amend,clarify,plan}.md` mirrors. All three `framework/commands/` sources were read in full and `scripts/gen-claude-commands.sh` ran in the same pass reporting all sixteen commands in sync — good grounds to believe the mirrors correct, and not a read. Recorded `examined: 8` over `scope: 11`, naming the three and the reasoning. This case recurs on **every** spec that touches `framework/commands/`, since each such spec pulls its generated copies into scope, so it is a standing judgment rather than a one-off. How to apply: count only what you opened. Name the rest individually in the Summary with *why* you did not open it and what you relied on instead — "generated from a source read in full, generator re-run and reported in sync" is a complete answer; "it's generated" is not. The same rule covers a file too large to read fully (say which parts you read) and an in-scope path that no longer exists (it stays in scope because the plan lists it, and is named as absent).
- **Never record another project's name in this repository — describe the shape instead.** Specs, scenarios, changelog entries, commit messages and runtime doc comments may say *what kind of project* exercised something (a pre-042 adopter with a legacy root config, an `.mcp.json` naming the bare command) but not *which one*. What a reader needs is the shape they must reproduce; the identity is the maintainer's local context and does not survive outside this machine. Reason: confirmed by the user 2026-08-17 — the project used to validate 048's AC10 had accumulated 13 references across 8 files including runtime source, and the user's ruling was that *"another project does not need to be recorded in this one."* How to apply: when a defect is found by running against a real adopter, write the reproducing conditions and drop the name; if a fixture is useful, build one under `/tmp` or in `tests/`. Sweeping a name out afterwards is a uniform token substitution, so done specs stay `done` — but the replacement text usually varies by sentence, which means `mechanical_sweep`'s repo-wide test will *not* exempt it and reviews touching those contracts go stale. Expect to re-review; that is the cheap direction of error.
- Read `framework/commands/{name}.md` before recommending, describing, or disambiguating a slash command — don't guess from the name. Source files are authoritative; the generated `.claude/commands/ductus/*.md` copies are produced by the pre-commit hook.
- **A `.ductus/config.toml` change is cross-spec impact only when it modifies a key another spec already documented.** The rule is [§cross-spec-impact](framework/constitution.md#cross-spec-impact) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-10 while clarifying spec 020 — adding `[review] tech-stack-verified` did not warrant reopening 019. How to apply: only treat a `.ductus/config.toml` change as cross-spec impact when it modifies an *existing* key already documented in another spec.
- **A retired feature's spec is deleted, not left at `done`.** The rule is [§spec-lifecycle](framework/constitution.md#spec-lifecycle) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: confirmed by the user 2026-09-05, after `/ductus:status` was mis-summarised here as showing spec 052's feature retired while its spec stood at `done`. The summary was wrong — 054 removed only 052's *supersession* half and its consolidation half still ships — but the principle the user drew from it is right and was already the framework's practice without being written down: 054's AC18 deleted **053**'s directory outright, because 053 shipped reconciliation alone and nothing in it survived. That deletion happened by one spec's explicit acceptance criterion rather than by a standing rule, which is exactly the diligence dependency [§design-principles](framework/constitution.md#design-principles) rejects — the next retirement had nothing to make it happen. How to apply: when a feature is removed, remove its spec directory in the same change; use `/{project}:consolidate` when the content belongs with another spec, since it re-points inbound pointers before removing anything. Retiring part of a feature is an ordinary body edit — the spec stays and describes what remains. Nothing enforces this yet; it is convention plus the command, the same footing the analyze record had before spec 047 gave it a gate. **First applied 2026-09-13 to `005-workflows`**, whose backfill pass opened and found 043 had removed the whole workflows feature. The worked example is worth keeping because two things about it generalise. **The decision it reversed was correct when made:** 043 resolved *"Spec 005 keeps `status: done` and gains a sunset note"* on 2026-07-22 (`062e2d45`), and the rule contradicting it landed 2026-09-05 (`970b8322`, spec 050) — six weeks later. Nothing detects a decision overtaken by a later rule, which is why reading Resolved Questions as live claims is a campaign step rather than a courtesy. **And the machine re-point was the wrong tool:** `rewrite-spec-links` aims every inbound link at the target, which would have made 019's data-model say the category set was *defined in* 043 when 043 **removed** it, and would have turned 043's own three references into self-links that `derive-dependencies` records for the cycle check. Hand-correct the referrers first, then run the primitive as a proving no-op — `rewritten: []` against `examined: 418` is what distinguishes *checked and found nothing* from *nothing checked*. **Corpus surveyed the same day for other candidates: none.** Two independent signals, because the obvious one is blind on its own. (1) Superseded-criteria ratio: 26 specs carry at least one annotated-as-removed criterion and **none exceeds 53%** (054 at 53%, 042 at 37%, 010 at 35%), so every one retains a majority of live criteria — but this sees only criteria somebody *annotated*. (2) The migration registry, which is the framework's own record of what it has removed: of its twelve entries only three are feature removals rather than renames or relocations — `spec-and-plan-sunset`, `generator-primitives` and `workflows-sunset` — and the first two trace to 000 and 017, both of which delivered far more than the removed surface. The three highest from signal (1) were then checked against the tree directly: 010's `--auto` and stuck detection still ship, 042's `.ductus/` exists, and 054's delivery *is* a removal that still holds — a removal spec's product is an absence, and `done` stays correct while that absence does. **The blind spot, stated because it is the part neither signal covers:** a capability removed *internally*, with no adopter-facing migration and no criterion annotation, is invisible to both. A removal that reached adopters needs a registry entry (spec 027), so the exposure is confined to framework-internal removals. How to apply: ask the question at **removal time** — when a spec removes a feature, name its introducing spec and decide whether anything it delivered is still true — rather than re-running a corpus survey that is empty by construction until someone forgets.

The disposition differs too — a superseded criterion is annotated with what replaced it, while one that was never true is annotated with what it actually described, and **neither is a licence to sweep the artifact**: 023's divergence is correct (`status` renders a view of every spec, `target` recommends the action on the one just selected), so changing `status.md` to match would have altered shipped behaviour on the strength of a stale claim.

## Gotchas

- **After changing runtime source, verify through the built binary — not the MCP tools.** The `ductus` MCP server runs the binary it was started with, so every `mcp__ductus__*` result in a session reflects the runtime as of session start, not your working tree. A primitive you just changed will keep reporting its old behavior, and the result looks authoritative. How to apply: after `cargo build --release`, verify with `./runtime/target/release/ductus <primitive> …` and treat MCP results for that primitive as stale until the server is restarted. **This bites hardest when the stale primitive *writes* rather than reads.** A stale read is a wrong answer you may catch; a stale write persists on disk and a later gate trusts it. Running a pipeline command in the same session that changed the primitive backing it is the concrete case — `/{project}:review` invoked after editing `write_review.rs` renders the pre-edit report, and `/{project}:analyze` after editing `write_analysis.rs` records the pre-edit block. Surfaced again 2026-09-11 on spec 055: the review of the very feature that added the `## Unexamined governance` section was written without it. Finish runtime work, restart the session, *then* run the pipeline commands that consume it. Reason: surfaced 2026-08-31 during spec 054 — `read-spec` returned a `supersedes` key the new code cannot emit, which read as a passthrough bug in the struct and was actually the old server answering; an acceptance criterion had already been marked verified on the strength of one of those stale results.
- **`framework/commands/help.md` is generated — hand-edits to it are reverted on the next commit.** `scripts/gen-help-tables.sh` owns its command tables and the pre-commit hook runs it, so removing a command by editing `help.md` puts the row straight back (with an empty description, since the source file it reads is gone). How to apply: change the entry in `scripts/gen-help-tables.sh` and re-run it; treat `help.md` as build output. The same ordering applies to `framework/bootstrap/configure/*.md`, which `scripts/gen-configure-mcp.sh` derives from `framework/runtime-tools.txt`. Reason: surfaced 2026-08-31 during spec 054's command removal — the hand-edited row came back on the very next commit.
- **Registering a runtime primitive is five sites, and two of them are only found by tests — de-registering one is the same five.** The obvious three are the CLI command enum plus its dispatch arm in `runtime/src/main.rs`, the exec-path match arm in `runtime/src/interpreter/mod.rs`, and the `#[tool]` in `runtime/src/mcp/server.rs`. The two that get missed are `framework/runtime-tools.txt` (the shipped manifest) and `runtime/src/schema/registry.rs`'s `PRIMITIVE_REGISTRY` (the canonical set). Reason: surfaced 2026-08-30 adding a primitive whose registry entry was missed, and `runtime/tests/mcp.rs`'s `lists_every_manifest_tool_and_canonical_set` caught it by asserting the manifest is set-**equal** to the registry: a manifest entry with no tool is a phantom, and a tool missing from the manifest escapes both the markdown-only PATH assertion and `scripts/lint-tool-coverage.sh`. How to apply: after adding a primitive run `cargo test --test mcp` before anything else — it names the exact divergence with both sets printed. Then run `scripts/gen-configure-mcp.sh` **followed by** `scripts/gen-claude-commands.sh` (that order; the second renders command copies from what the first writes) or `/{project}:audit`'s check-zero precondition fails on a stale `.claude/commands/ductus/configure.md`. A new arm may also push `dispatch_primitive` past clippy's 100-line ceiling; it carries the same `#[allow(clippy::too_many_lines)]` as `main`'s CLI match, for the same reason — both are flat registries that grow one arm per primitive.
- **`check-artifacts`' `skipped` array names targets that could not be *reached*, never subjects that were empty.** Its reason set is closed and each entry points at a path something tried and failed to examine. A family with nothing to examine — no declared edge, no path claim — reports neither a finding nor a skip. Reason: surfaced 2026-08-30 building a check family whose first implementation recorded a skip on every spec that declared nothing for it to examine, to express that the family only sees declared edges. Six existing tests failed, correctly: they encode the contract. Overloading the set would have put an informational line on every spec in a corpus while telling an operator nothing actionable. How to apply: when a family's coverage is genuinely bounded, state the bound in the family's doc comment and in `framework/commands/analyze.md`'s rendering — where a reader meets it once — rather than emitting a per-spec entry. Removing the skip made all six tests pass untouched, which is the tell that the contract was right and the design was wrong.
- Use `npx markdownlint-cli2` to run markdown linting — do not suggest installing it globally.
- **A prose-only edit to `framework/commands/*.md` can break a Rust test, so run `cargo test` before calling such a change verified.** `runtime/tests/parity.rs`'s `read_parity_spec` prefers the repo-canonical command file over any fixture copy, so that file's *bytes* land in the parity fixture's git tree. `init_git_repo` then commits with a frozen signature — deliberately, because `derive-boundary`'s `first-commit` / `current-head` are threaded into the `writeCode` payload and a drifting sha would make the golden flaky. Frozen time plus a fixed tree fully determine the commit OID, so changing the tree changes the OID *by design*. Only `implement-basic.jsonl` is affected today; it is the one golden whose payload carries git-derived values, and the other ten pass untouched when the same commit edits their sources. Re-bless it with the test **filtered to that one golden** (`BLESS=1 cargo test --release --locked implement_basic_stream_matches_golden`), never a corpus-wide `BLESS=1`, then confirm the diff is only the two sha fields. Blessing does preserve `{{runtime-version}}` — `parity.rs:730` templates the literal back before writing — so the release entry's warning below is about not needing a re-bless for a version bump, not about this path. Reason: surfaced 2026-08-19 — spec 040's `spec-root-rule-stated-once` deleted a blockquote from six command sources; markdownlint, procedure-parseability, the derived indexes, the generators, and the full self-audit were all green locally, the change was reported as markdown-only, and CI then failed on all three platforms. How to apply: treat every file under `framework/commands/` as **runtime-adjacent** — the local gate for any edit there is the full CI surface (see Workflow), not the markdown checks alone.
- The command generator substitutes `{project}` → `ductus` and `{cli-config-dir}` → `.claude`, and writes the Claude-specific permission file (`framework/bootstrap/configure/claude.md`) as `configure.md` in the `ductus` command directory. The values are `PROJECT` and `CONFIG_DIR` in `scripts/gen-claude-commands.sh`; they read `gov` until 049 renamed the project.
- **An edit to `framework/commands/*.md` is invisible to that slash command until the generator re-runs — including to the command you are editing, in the same session.** The pre-commit hook regenerates `.claude/commands/ductus/` (see Workflow), but that is *commit* time; the agent host loads the installed copy at *invocation* time. So editing a command source and then invoking that command walks the pre-edit text, silently. The same shape applies one layer down, but the loop is shorter than it used to be: this repo sets `[runtime] path = "runtime/target/release/ductus"` and registers the pointer (`.ductus/bin/ductus`) as the MCP command, so a `runtime/` source change is live for MCP tool calls after `cargo build --release` **and** an MCP server restart — which means a new session, since the host spawns the server once. There is no `cargo install` step and `PATH` is not consulted; the pointer resolves straight to the build in the working tree. Reason: surfaced 2026-08-14 — `framework/commands/analyze.md` was corrected to document `--fix`'s second trigger, and the very next `/ductus:analyze` invocation loaded the stale installed copy and displayed the old text; in the same session the `append-*` marker fix was published as `gvrn-v0.27.2` while every MCP call kept using the Aug-3 binary (that half is what `[runtime] path` now prevents — spec 048). How to apply: after editing any `framework/commands/*.md`, run `scripts/gen-claude-commands.sh` before invoking that command (it is idempotent, and the pre-commit hook re-runs it anyway); after a `runtime/` change, do not trust an MCP tool call in the *current* session to exercise it — verify with `cargo test`, and treat the running server as the pre-build binary until the session is restarted.
- `.claude/commands/ductus/init.md` is the one exception to the generator rule — it is `ductus`-specific (no source counterpart) and is hand-maintained. The generator leaves it untouched.
- **Never `git add -A` / `git add .` in this repo.** The rule is [§text-first-artifacts](framework/constitution.md#text-first-artifacts) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Here it bites on in-progress `specs/NNN-*/spec.md` drafts from `/ductus:specify`, which spec 017 (`tracked-specs-not-worktree`) forbids sweeping into a commit. Stage explicit paths.
- **The two frontmatter derivations are runtime primitives, not shipped scripts.** `dependencies:` and `references:` are derived by `ductus derive-dependencies` and `ductus derive-references`; the adopter-facing generator scripts that used to own them were removed by spec 022's `adopter-generator-promotion` (migration `generator-primitives`). Reason: §runtime-boundary principle 3 names shell pipelines that parse frontmatter or markdown structure as **not** a sanctioned substitute for a primitive, and the constraint that had kept them in shell — the runtime being optional — was retired by spec 048. Three defects reached adopters through that shell on 2026-08-17, all silent and all exit 0. How to apply: a new derivation over spec frontmatter is a primitive wired at the six Rust sites plus `framework/runtime-tools.txt` (see the entry above), invoked from the hook as `ductus <name> --write --staged`. Do not scaffold a new generator script into the adopter's tree — there is no longer a Shared Files row, a permission entry, or a pin path for one.
- `write_atomic_bytes` (the create-then-rename helper backing every primitive write) lands the destination at the fresh tempfile's mode — `0600` on Unix — discarding whatever mode the file should carry. For markdown/JSON this is invisible (git tracks only the exec bit), but a primitive that writes a file expected to be **executable** must re-apply the mode itself. `apply-manifest` mirrors the *source* file's `Permissions` onto the dest after each write (`mirror_source_mode`, `cp -p` semantics) because the **Shared Files** manifest ships executables — `framework/bootstrap/hooks/ductus-pre-commit` with `update` strategy and `hooks/pre-commit` with `create` — and git must be able to exec them; the staging source carries `+x` because `extract-archive` preserves archive-header modes (`apply_unix_mode`). The rule's original subject was the shipped `.ductus/scripts/gen-*.sh` generators, retired by spec 022; the hooks are what exercises it now, and `create-feature` calls `mirror_source_mode` for the same reason. Reason: surfaced 2026-06-30 — a `/ductus` run rewrote the generators to `0600`, failing the pre-commit hook (and a fresh adopter's `created` write would emit a non-executable generator + broken hook). How to apply: any new primitive writing an executable (or otherwise non-`0600`) file must restore the intended mode after `write_atomic_bytes` — do not assume the helper preserves it; mirror the source's `Permissions` when copying, like `apply-manifest` and `extract-archive` do.
- `runtime/rust-toolchain.toml` pins `components = ["clippy", "rustfmt"]`, and every `cargo` command run under `runtime/` makes rustup honor that file — auto-installing any missing component *mid-build*, a path that hits rustup's `detected conflict: 'bin/cargo-fmt'` bug and aborts the job. So any CI job that runs `cargo` under `runtime/` must pre-install those components via the `dtolnay/rust-toolchain` step's `components: clippy, rustfmt` input, so nothing is left for the runtime auto-install path to do. `runtime.yml` (which lints) always had it; the fix is to keep every other `runtime/`-touching workflow in sync. Reason: surfaced 2026-07-11 — the `gvrn-v0.16.0` release failed because `runtime-release.yml`'s `dtolnay` steps omitted `components:`; the `aarch64-unknown-linux-gnu` cross job's first `cargo` call (`cargo install cargo-zigbuild`) triggered the auto-install conflict. It was the first release tagged after the toolchain pin (commit 19d9229), so no earlier release exposed it. How to apply: when adding or editing a workflow that runs any `cargo` command from `runtime/`, give its `dtolnay/rust-toolchain@<ver>` step `components: clippy, rustfmt` matching `rust-toolchain.toml` — do not rely on rustup's toolchain-file auto-install to supply them.
- A new `ductus` runtime primitive wires into more than `primitives/mod.rs` + `mcp/server.rs`. Building and exposing it over MCP needs `schema/primitives.rs` (Args/Result types), `primitives/<name>.rs` + `primitives/mod.rs` (`pub mod`), and `mcp/server.rs` (`TOOL_NAMES` + a `#[tool]` method). Three more sites are needed the moment a slash command *uses* it: `parser/mod.rs` (`PRIMITIVE_NAMES`) so a command's `## Instructions` can backtick the name without failing `lint-procedure-parseability`; `interpreter/mod.rs` (`dispatch_primitive` match arm) so `runtime exec` can call it (the path the parity tests drive); and `main.rs` (`Command` enum variant + dispatch) for the `ductus <name>` CLI surface. Add the name to `framework/runtime-tools.txt` for `lint-tool-coverage`. Reason: surfaced 2026-06-14 implementing spec 030's `resolve-references` — MCP exposure alone passes `cargo test`, so the gap stays invisible until a command references the primitive. **Know which sites are pinned and which are not** — this entry previously said `tests/mcp.rs` "only checks `TOOL_NAMES ⊇ runtime-tools.txt`", which understates it, and `schema/registry.rs` overstated the other half. Verified 2026-09-11 by deleting each wiring in turn and running the suite: `framework/runtime-tools.txt` is asserted **set-equal** to `TOOL_NAMES` (`BTreeSet` == `BTreeSet`, `tests/mcp.rs`), so a missing entry *and* a phantom entry both fail; the `#[tool]` methods are pinned by `tests/mcp.rs` listing tools against `TOOL_NAMES`; `dispatch_primitive` is pinned by `interpreter::tests::dispatch_handles_every_registry_primitive`; and `parser/mod.rs` cannot drift at all, since `PRIMITIVE_NAMES` is a direct alias of `PRIMITIVE_REGISTRY` rather than a second list. **The clap subcommand enum in `main.rs` was the one unpinned surface, and is now pinned too** — `main::tests::every_registry_primitive_has_a_clap_subcommand` (022 task 110, `ductus-v0.48.0`) compares the names clap exposes against `PRIMITIVE_REGISTRY` by set-equality, so a missing variant and a phantom subcommand both fail, each naming the exact divergence. `exec`, `mcp`, `parse` and clap's synthesised `help` are excluded by name in `NON_PRIMITIVE_SUBCOMMANDS`, each with its reason: a primitive that should genuinely have no CLI surface is added there explicitly, never by loosening the assertion to containment. **There is no longer a surface to check by hand** — the earlier `cargo run -- <name> --help` step this entry prescribed is discharged, and `runtime/CHANGELOG.md`'s 0.47.0 note still describes the pre-0.48.0 state because a shipped release note records what was true then. How to apply: decide up front whether a command will reference the primitive; if yes, wire all six Rust sites + `runtime-tools.txt` in the same change.
- **A new slash command wires into five places outside `framework/commands/`, and two of them are load-bearing for adopters.** Adding `<name>.md` under `framework/commands/` gets it dogfooded here for free — `scripts/gen-claude-commands.sh` globs the directory — which is exactly why the adopter-facing half is easy to miss. The five: the **Shared Files** manifest table in `framework/bootstrap/ductus.md` §Per-Agent Scaffolding → Slash commands (without a row the command never reaches adopters, and §Slash command cleanup *deletes* it if hand-placed); `framework/bootstrap/govern.md`, the retired transitional bootstrap path that audit Family 21 holds byte-identical to `ductus.md`, so it takes the same edit (`cp framework/bootstrap/ductus.md framework/bootstrap/govern.md`); an entry in the appropriate `*_entries` group in `scripts/gen-help-tables.sh`, then re-run it to regenerate `framework/commands/help.md`; the command-name list in `runtime/src/parser/mod.rs`'s `rewritten_command_files_parse_with_document_step_numbers`, which asserts the file's steps number monotonically 1..N; and `scripts/gen-claude-commands.sh` re-run so `.claude/commands/ductus/` matches. Reason: surfaced 2026-08-29 adding `/ductus:fold` for spec 051 — Family 16 (`installer-command-parity`) pins the manifest to the source files and Family 21 pins `govern.md`, so `scripts/audit/run-all.sh` catches both, but only if you run it: the full `cargo test` + markdownlint surface was green with the manifest row missing. How to apply: make all five edits in the same change as the command file, then run `scripts/gen-claude-commands.sh` followed by `scripts/audit/run-all.sh` — in that order, because the audit's `check-zero` precondition fails on the un-regenerated installed copies before any family runs. Maintainer-only commands deliberately withheld from adopters are listed in `installer-command-parity.sh`'s `excl` block; add a line there instead of a manifest row.
- `<!-- audit:ignore-promotion -->` silences the framework self-audit's Family-9 (primitive-promotion) check for a prose-only `## Instructions` step, but it does **not** change how the runtime's exec parser reads that step. The parser (`parser/mod.rs`) marks any step naming a `PRIMITIVE_NAMES` token in a backticked code span as a primitive dispatch, and `lint-procedure-parseability` only rejects a step naming *two or more* primitives — a step naming exactly one is legal. So a host-responsibility step marked `audit:ignore-promotion` that mentions a primitive in backticks (e.g. a `--fix` action described "via `set-status`") gets dispatched by `runtime exec`, which then errors or performs an unintended mutation. Reason: surfaced 2026-07-12 — `/ductus:analyze` step 13 (report render, a host responsibility) referenced `set-status` in backticks; the exec walker dispatched it and the `analyze` parity golden failed with a non-zero exit, even though the parseability lint passed and the audit ignored the step. How to apply: in a numbered `## Instructions` step, backtick a primitive name only when the step is meant to *dispatch* it. To reference another primitive without dispatching — a leverage note, a cross-reference — name it without backticks, or move the reference into non-step prose (the command's preamble or its Markdown-only reference), where multiple primitive names can be backticked freely. `audit:ignore-promotion` is about the audit, not the parser.

- **A markdown link in a spec body creates a `dependencies:` edge — cite in prose when you mean a citation.** The rule is [§text-first-artifacts](framework/constitution.md#text-first-artifacts) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-16 — a link to `013`'s `review.md` from `049`'s body made the generator add `013-text-first-artifacts` to 049's dependencies, which is false (049 does not depend on 013; it merely cites it). The pre-commit hook applied it before anyone looked. How to apply: to cite without an edge, use a backticked slug (`` `013-text-first-artifacts` ``) rather than a link, or place the link under a §See Also region, which spec 017's `skip-prose-cross-references` opt-out already exempts. After editing a spec body, read the `dependencies:` line in the hook's output before committing — the generator reports `Updated …` when it rewrote one.
- **`create-scenario` appends its own Open/Resolved Questions scaffolding — do not author those headings in the body you pass it.** The rule is [§scenarios](framework/constitution.md#scenarios) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-16 grooming an inbox item into a scenario carrying one real open question. How to apply: pass Context / Behavior / Edge Cases only, then edit the scaffolded `## Open Questions` section afterwards to add entries — or write the whole file with `Write` if it needs questions at creation time.
- **A version bump needs one build without `--locked`.** Every other runtime command in this repo uses `--locked`, but bumping `runtime/Cargo.toml`'s `version` changes the package's own entry in `Cargo.lock`, and `--locked` exists to forbid exactly that (`error: cannot update the lock file … because --locked was passed`). Run `cargo build --release --offline` once to refresh the lock, after which `--locked` works again. Reason: surfaced 2026-08-16 cutting `ductus-v0.28.1`. How to apply: bump, one `--offline` build, then verify `--locked` succeeds before committing — and remember the release binary must be rebuilt anyway, because `runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time and a stale binary fails the parity version line. Never `BLESS=1` to absorb that failure; it would replace the `{{runtime-version}}` placeholder with a literal.
- **Never write a literal `ductus-vX.Y.Z` into a `framework/commands/*.md` prose line — `BLESS` will template it into a time bomb.** `runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` for `{{runtime-version}}` when it compares, and re-blessing applies that substitution in reverse over the *whole captured stream* — so a command source whose prose happens to name the **current** version has that literal rewritten to `{{runtime-version}}` inside the golden. The golden then renders next release's version where the source still says this one's, and the parity test fails on a line nobody touched, one release later, with a diff that looks like a version bug rather than a prose bug. Reason: surfaced 2026-09-12 landing 022's inbox row. Step 15 of `implement.md` cited `ductus-v0.47.0` as the release that shipped over a full inbox; `BLESS=1` on `implement_basic_stream_matches_golden` turned it into `ductus-v{{runtime-version}}` in the golden, visible only because the bless diff was read line by line before committing. The same shape would bite any file whose bytes reach a golden. How to apply: in a shipped command source, describe the release without naming it (*"a release has shipped with an obligation outstanding"*) — the version is meaningless to an adopter reading that file anyway, which is the second reason not to write it. Keep the dated, versioned account in `runtime/CHANGELOG.md`, the spec, or the scenario, none of which are staged into a parity fixture. And read a bless diff in full: the version-bump entry above warns against blessing to absorb a version delta, and this is the same trap approached from the other side — a bless that looks like it changed only what you edited can have rewritten a literal you did not.

- **Gitignored adopter state survives a `git` reset, so a "reset" subject is not a fresh one.** Reverting a test adopter restores tracked files and nothing else: `.mcp.json` is gitignored in many projects, `.ductus/bin/` always is, and the runtime store lives outside the repo entirely at `~/.ductus/bin/ductus`. Reason: surfaced 2026-08-17 across two 048 AC10 runs. After the first run was reverted, `.mcp.json` still carried the converged `ductus` entry from that run, so the retired-key collision the second run existed to exercise was absent until it was restored by hand; the store still held the previously acquired binary, turning fresh acquisition into an upgrade. How to apply: before re-running a bootstrap test, list what the scenario needs to be true and check each against the working tree rather than assuming `git` restored it — for a pre-rename subject that means the MCP config's server key and command, the absence of `.ductus/bin/`, and the store's version against the pin. Capture the pre-run shape of any gitignored file you will want back *before* the first run; it cannot be recovered from history afterwards.
- **This repo's dogfooded copy of an adopter file is not the copy adopters get — test the shipped one.** `.githooks/pre-commit` (ours) and `framework/bootstrap/hooks/ductus-pre-commit` (shipped) are *separate files* doing the same job, and the same split existed for the shipped generator scripts until they became runtime primitives. A guard present in the copy this repo executes is invisible to adopters — and worse, the dogfooded copy working is exactly what stops anyone noticing the shipped one is broken. Reason: surfaced 2026-08-17, twice in one adopter run. The shipped hook guarded `label-criteria` on `command -v ductus`, but spec 048 moved the runtime into the ductus-owned store and `/ductus` never puts it on `PATH`, so spec 013's labelling backstop was dead for **every** adopter since 048; our `.githooks/pre-commit` has a `runtime/target/release/ductus` tier ahead of the `PATH` fallback and worked fine, which is why it went unseen for four releases. In the same run, `config_path_of` in the shipped their shared spec-root helper had no `.ductus/` tier and resolved a *converged* adopter to a nonexistent legacy path, silently defaulting their spec root — masked here because this repo uses the default `specs`. Both failed silently and exited 0. How to apply: when touching `framework/bootstrap/hooks/` or anything else the manifest ships into an adopter's tree, ask what the **adopter's** copy does and exercise it against a tree shaped like theirs, not this one — `bash -c 'cd <adopter-checkout>; …'` or a `/tmp` fixture is enough, and takes seconds. A green run in this repo is evidence about this repo. This is the [check that cannot run](#design-principles) principle applied to the gap between what we dogfood and what we ship.
- **A spec's review diff base moves forward on every reopen, so the window shrinks — measure it before reaching for `--since`.** `compute-review-scope` derives the base from the **newest** commit at which the spec entered `in-progress`, not the first: `find_in_progress_commit` walks the whole history and keeps the last transition whose parent was not already `in-progress`, then the base is that commit's parent. Every `done → in-progress` back-edge therefore moves the base forward, and a spec's file count is a snapshot of where it last reopened rather than a standing property of the spec. Reason: this entry used to name `020` and `022` as carrying bases that "predate the `0.28.0` cycle", quote 677 and 551 modified-since files measured on 2026-08-18, and conclude the scope "can only grow" — all three went false as both specs were reopened and re-closed, and nothing was watching for it because the numbers read as facts about the specs rather than about that date. - **Piping a gate command's output replaces its exit status — `cmd | tail` reports `tail`'s success, not `cmd`'s.** A `&&` chain, a captured `$?`, and `set -e` all read the *pipeline's* status, which is its last element's. So `cargo test --release --locked 2>&1 | tail -25` exits 0 over a failing suite, and `cargo clippy … -- -D warnings | tail -3` exits 0 over a warning. `set -o pipefail` fixes it and is **not** on by default in an ad-hoc `Bash` call — this repo's scripts set it in their preamble, and the one-off verification commands nobody reviews do not, which is exactly where it bites. Reason: surfaced 2026-09-12 — the full local gate was reported green on the strength of `cargo fmt --check && echo ok && cargo clippy … | tail -3 && cargo test … | tail -25`. Both piped legs returned `tail`'s status; the chain could not have failed. A re-run capturing the real statuses is the only reason the claim was not simply wrong. This is the [check that cannot run](#design-principles) principle turned on the verification step itself: the output *shown* was genuine and the *status* was manufactured by the pipe. How to apply: never pipe a gate command whose exit code you intend to read. Redirect and read the status on the line that ran it — `cargo test … > /tmp/t.out 2>&1; echo "exit=$?"` — then grep the file. Reading the tail is its own half of the trap: the last 25 lines of a multi-binary `cargo test` show one binary's result and hide nineteen, so count `^test result:` lines against the number of binaries rather than eyeballing the end.

How to apply: before a sweep, `git grep` the pattern restricted to `'specs/*/scenarios/*.md' 'specs/*/data-model.md'` and decide each hit deliberately — sweep it and accept the re-review, leave it, or defer it into a pass that will re-review anyway. Then run `run-all.sh` **after** the commit, always.
- **`criterion-path-existence` only sees a path inside backticks — an unbackticked one is not a finding, not a skip, and not a candidate.** `check_artifacts.rs`'s `candidate_paths` walks `inline_code_spans(line)` and nothing else, so a criterion naming a path in plain prose is invisible to the family entirely. That is a worse silence than the `skipped` array §Workflow already warns about: a skip at least *names* the criterion nothing checked, while a bare path produces no record at all, and the family still reports `clean: true`. Reason: surfaced 2026-09-13 on 010. Its `check-artifacts` reported six `not-a-live-claim` skips, all from AC14 — whose paths are backticked — while AC5 and AC6 named `commands/` and `ductus/` in plain text. Both were dead: the first was reorganised into `framework/commands/` and the second is where 049's token sweep rewrote `govern/` (the bootstrap installer variants, now `framework/bootstrap/`) onto a path that never existed on disk. Two stale paths stood in a `done` spec across every release since, and no run of any check had ever had them as a subject. **Backticks are necessary but not sufficient, and that half cost a second spec.** `is_path_like` requires an **interior** `/` — it tests `content.trim_end_matches('/').contains('/')` — so a bare top-level directory and a bare filename are rejected as candidates even when correctly backticked. Measured 2026-09-13 on 007, whose AC1 read *"One `ductus.md` variant exists per supported CLI in the `ductus/` directory"*: `ductus/` trims to `ductus` and `ductus.md` never had a slash, so **both** dead paths were invisible, `check-artifacts` reported `clean: true` with an empty `skipped`, and the criterion stood ticked from 2026-05 through every release since. Two other families are quiet on a `done` spec for reasons worth knowing at the gate: `scenario-consistency` is **skipped for `done` specs** by design (tasks may legitimately be pruned), and **nothing checks the reverse direction at all** — that a task's named `scenarios/{slug}.md` exists. 007's task 6 pointed at a file 049's sweep had renamed in the task text but not on disk, and no family looks that way. How to apply: at the completion gate, read the criteria for paths **yourself** and do not let a short `skipped` array stand in for that — the array's length is a fact about backticks and slashes, not about claims. When you correct one, backtick it **and give it at least one interior `/`** (`framework/bootstrap/ductus.md`, not `ductus.md`), which is what actually brings it under the family for the next reader. **An interior slash is necessary and not sufficient — the path must also be repo-relative**, because `candidate_paths` tests `repo.join(trimmed).exists()` (`check_artifacts.rs:1250`), so a spec-relative `scenarios/{slug}.md` written inside that spec's own criterion resolves against the repo root, finds nothing, and is recorded as a `root-absent` skip rather than checked. Measured 2026-09-14 on 040, where a pass's own annotation took `unexamined` from 2 to 3 that way and spelling the same path `specs/040-configurable-specs-dir/scenarios/…` took it back to 2 while turning three path claims from skipped into verified. The spec-relative form is the natural one to write and the one `tasks.md` uses, which is exactly why it is worth stating. This is the [check that cannot run](#design-principles) principle one level further in than the entry that records it: there the check said what it had not examined, here it had nothing to say. **`clean: true` arrives in three shapes and they are not interchangeable — read `skipped` against the span count, never on its own.** Measured 2026-09-14 across two passes in one session. **051**: `skipped: []` over **37** backticked spans, of which **0** are path-like — and walking all 37 showed why, which is that *none of them is a path claim at all* (identifiers, grammars, statuses, frontmatter keys, command names). There was nothing for the family to check even in principle, and no correction could have brought one under it. **023**: **24** skips over **182** spans of which **59** are path-like, so the array is a genuine worklist and the family was doing its job loudly. **000** (walked 2026-09-14): exactly **one** skip, reason `ships-to-adopter`, which is an *exclusion by construction* rather than something unchecked — and it is the **only** path-like span among the **22** backticked spans in its 15 criteria, so not one path claim in that spec had ever been checked, and no correction could have brought one under the family either. All 22 were walked by hand. Its `unexamined` then **held at 1** while the pass's annotations took the spans 22 → 30 and the path-like candidates 1 → 2, because the one new candidate (`.ductus/session.toml`) was written **repo-relative** and therefore resolves instead of landing as a `root-absent` skip — 040's lesson applied ahead of time rather than rediscovered, and the first pass in the campaign where the count was predicted correctly. So an empty array means either *nothing was checkable* or *everything checked out*, and only the span count separates them: `0 of 37` and `59 of 182` are opposite situations wearing the same result. Count the path-like spans before reading anything into the array's length. **And the repair runs both ways — a pass's own annotation can manufacture the finding it documents.** Same session, on 051: the AC5 correction spelled two *illustrative* link targets as concrete paths (`../1234.1-slug/spec.md`), which `is_path_like` accepted and `criterion-path-existence` reported as **two advisory findings** against files that were never meant to exist. Restating them as `{identifier}.{n}-{slug}` asserts the same thing and is invisible to the family, which is the honest shape for a grammar rather than a file — the inverse of 040's repair, and the reason the family is re-run **after** the status flip rather than trusted from before it.
- **A spec's own completion commit can destroy content, and a `## Heading` absorbed into an unterminated code span is invisible to every check this project has — including the gate that reads it.** Measured 2026-09-14 on 000. `ccdd3ac6` (*feat(000): slash commands reaches done*) — the very HEAD 000's review was recorded against — resolved `criterion-route-after-draft.md`'s two open questions and, in the same edit, dropped four Edge Case bullets and cut the fifth mid-sentence at an **opening** backtick, swallowing the `## Open Questions` heading that followed into the span. It stood for four weeks and every gate stayed green. **Proven by probe rather than by reading:** two scenarios built with byte-identical question content, one intact and one with the heading swallowed — `read-spec` reports the intact one's question and omits the damaged one's **entirely**, so the pre-`done` gate's unresolved-scenario-questions check was satisfied *by* the damage rather than despite it, and a spec reached `done` partly because a heading stopped being a heading. What is blind to it, each checked: the repo's own `markdownlint-cli2` reports **0 issues** on the damaged file under `.markdownlint-cli2.jsonc` (an unclosed backtick never becomes a code span, so MD038 does not fire); `check-artifacts` reports `clean: true`; and `check-corpus-links`, `resolve-anchor` and `derive-dependencies` all read past it. `/{project}:audit` Family 25 (`unbalanced-inline-markup`) is the one check that catches this shape, and its `TARGETS` are exactly `AGENTS.md` and `framework/templates/project/agents.md`. **Do not widen Family 25 to the spec corpus** — its own header records the measurement that scoped it: spec prose wraps freely, so a per-line check would trade two real findings for **283** false ones. That bound is correct; what is missing is any corpus-side check at all, which is stated here rather than implied. How to apply: when a commit's purpose is to **remove** a section — resolving questions, deleting a superseded block — diff the *structure*, not only the prose. `grep -c '^## '` before and after costs a second, and an edit anchored on a string that also occurs inside a code span will silently consume everything between the two occurrences. The tell 000 offered and nobody took: a sibling scenario showed `## Open Questions`, then its *None* line, then `## Resolved Questions`, while the damaged one showed only the middle line.

## Boundaries

- **No host-level enforcement of the deterministic (`ductus`) path — it is a deliberate non-goal.** `/ductus`'s State-A execution contract (spec 029, scenario `state-a-deterministic-path-forcing`) uses binding *procedure language* to get a wired runtime actually used. `ductus` does **not** enforce it at the host level — no denying `curl`/`tar` while `ductus` is registered, no State-A-only procedure variant with the shell stripped. Reason: host enforcement would block the legitimate non-primitive shell steps the bootstrap needs (gitignore `curl`, `git config`, `chmod`), is host-specific and a permanent per-host maintenance tax, and breaks [§runtime-boundary](framework/constitution.md#runtime-boundary)'s "neither path wraps the other" parity by demoting the markdown path. A model that ignores the binding contract falls back to the correct-but-pricier markdown path — an accepted outcome, not a gap. How to apply: do not propose or build host enforcement as a follow-up; if the procedure-level contract proves insufficient for a given model, the answer is a more capable model, not coercion.
- **Never edit an installed command file directly — edit the source the generator copies from.** Here that means never editing `.claude/commands/ductus/*.md`; your changes are overwritten the next time the generator runs. Edit the source under `framework/commands/` (or `framework/bootstrap/configure/claude.md` for the `configure` command). The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-23 during the spec-022 `/ductus:status` rewrite — I read the deployed (already-substituted) copy when drafting the rewrite and shipped hardcoded `/ductus:` and `.claude/` literals to the source, which broke the framework-checks CI on Family 4 of `scripts/audit/run-all.sh` (`placeholder-roundtrip`). How to apply: when in doubt, `git show HEAD:framework/commands/{name}.md` to see the source convention before editing; the `placeholder-roundtrip` audit is the post-hoc check, not the first line of defense.
- **Never end a response with a "worth flagging" / "worth noting" / "two things to note" section. Every residue gets a disposition, not a paragraph.** [§design-principles](framework/constitution.md#design-principles) already forbids this and names why it happens: for anything outstanding there are exactly three dispositions — fix it, record it where the pipeline will surface it again, or decide it is out of scope and record the reason — and "disclosing it in prose alongside a completion claim is none of the three, and it is the most tempting failure available because it feels like candour." A trailing notes section is that failure in its purest form. It reads as diligence while making three different states indistinguishable: something already fixed, something recorded and waiting on a command, and something merely observed all get the same bullet, so the reader cannot tell what is owed to them or by whom. Reason: surfaced 2026-09-07 and confirmed by the user, after a report on spec 047 closed with a "worth flagging" list that mixed one designed behavior already recorded in a scenario's Edge Cases, two findings already fixed with tests, and one item logged to `specs/inbox.md`. The user's words: "it's not clear whether things were identified and not addressed versus identified and addressed versus just a note. i don't want notes, it want actionable items otherwise i want relevant, durable information added to the constitution or rules." How to apply: before writing any closing section, give each item its disposition, then write the **disposition** rather than the item. *Fixed* belongs in the account of what was done — past tense, with the test that holds it. *Recorded* names the artifact it now lives in and the command that picks it up (`specs/inbox.md` → `/{project}:groom`; a scenario; an acceptance criterion). *Out of scope* says so with its reason. *Durable and general* is a constitution or rule change — or an entry in this file when it is local to this repo — and the response names the file that changed. An item that fits none of those four is not worth the reader's attention and does not go in the response at all.

## Design Principles

- **Reach for a runtime primitive first; a shell script is the fallback.** The rule is [§runtime-boundary](framework/constitution.md#runtime-boundary) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*. A capability that is deterministic, already mechanical, and specifiable as prose meets the eligibility criteria, and meeting them is a **default, not a permission**: it is implemented in `runtime/` and the shell entry point the framework needs — a pre-commit hook, a CI step, an `/audit` family — resolves the binary and calls the primitive. `scripts/audit/command-flag-hint-parity.sh` (Family 30) is the reference shape: the check *is* the `check-command-flags` primitive and the script is ~40 lines of entry point. Reason: surfaced 2026-08-28, twice in one session, each time as a script written by reflex and corrected only after the user pushed back. The second was `/audit` Family 31, where a hand-rolled `scalar()` helper — copied from `review-freshness.sh`, which still has it — used `\s*` after the key, and because `\s` matches a newline it walked past an empty value onto the next line and returned *that* line's content, producing a confidently-wrong finding against a spec that was correct. The runtime's tested scanners do not have that bug, and the copy that did was the fourth hand-rolled frontmatter parser in a repo whose runtime already parses frontmatter for a living. How to apply: before writing a script, ask what stops this from being a primitive and answer with a criterion that fails, not with "a script is faster to land" — the build is a one-time cost to the author and the parser is a permanent cost to every reader. If the script would parse frontmatter or markdown structure to do its work, that is the signal it belongs in the runtime, regardless of whether it reaches for `awk` or for an embedded `python3` heredoc; the language is not what the principle turns on.

- **A check that cannot run must never look like one that passed.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*, not a second statement of it. It is the single most expensive failure mode this repo has produced. It surfaced four separate times while shipping `ductus-v0.28.0`, each time as a green signal that meant nothing: `scripts/audit/sibling-coupling.sh` used a GNU awk extension, so on every macOS machine the extraction aborted, the family found nothing, and it exited 0 — a release gate that was dead locally and alive in CI; `release-assets` in `runtime-release.yml` needed only `build`, so the self-audit gated the crates.io publish while the binaries adopters actually download shipped regardless; the acquisition workflow was triggered by `on: release: [published]`, which GitHub never fires for a release created with the default `GITHUB_TOKEN`, so the invariant the constitution requires would have been cited by name and never once executed; and the `macos-13` runner label no longer resolves, so that leg sat queued with no runner while the others passed — a missing runner reads as a hang, since it produces no step output. Reason: all four were invisible to a passing local check, and three of them were invisible in CI too until something else forced them into the open. How to apply here: the constitution states the rule; what is local to this repo is where it bites. When a job is a gate, check what actually depends on it rather than what its name implies. And treat a green local run of `scripts/audit/run-all.sh` as necessary-but-not-sufficient evidence before a tag — the environments differ in exactly the dimensions the checks depend on.

- **Never close work with a caveat attached — the status is the claim, and a summary is not where residue lives.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*. Reason: surfaced 2026-08-19, three times in one session and each time in a different place — a stale prose claim left standing while 022 went to `done`, a detection gap reported as unmeasured while 026 went to `done`, and both narrated in the closing summary as though naming them discharged them. The user's ruling: *"the work is either complete or it isn't. don't change the spec status to done and then say this."* The tell is that each caveat was **true**, which is exactly why the habit survives — it reads as candour and costs nothing to write. What it actually does is move the exception from a channel that is re-read (the status, the inbox, a scenario) to one that is read once (a summary, a commit message). When the second of those caveats was finally investigated it was 28 broken links, a number thirty seconds of grep would have produced at any point. How to apply: when you notice something outstanding while closing, do not reach for the summary. Fix it; or record it where the pipeline will resurface it and let the status follow that record; or record an out-of-scope decision with its reason. Reopening a `done` spec is cheap and routine — preferring a caveat to a back-edge, to keep a status field looking clean, is the failure in its purest form. And when the residue is only knowable by measuring, measure: an unmeasured gap is a task, not a caveat.
- **Never design framework features that depend on human diligence or discipline.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-06 when evaluating an optional `## Upgrade Impact` spec section as a way to capture cross-version migration notes; rejected on this principle and the topic was tabled to inbox until a derivable design is found. How to apply: this is a hard filter on framework proposals, not a tiebreaker — if the only viable design relies on author discipline, the right answer is to defer the feature, not to ship the disciplined version "for now."

- **Removing an embedded copy is a corpus sweep, not a deletion — grep for what pointed at it, including the artifacts that *describe* it.** Reason: surfaced 2026-09-13 replacing 020's §Embedded artifacts (a 561-line frozen copy of `framework/commands/review.md`) with a pointer, which took `spec.md` 803 → 275 lines. One deletion produced three separate corrections, and none was in the deleted section. **Inside the spec:** `data-model.md` said its shapes are referenced by "the spec body and embedded `framework/commands/review.md` artifact", naming a section that no longer existed; `plan.md`'s affected-files table said the **embedded artifact in spec.md is the canonical content**, which is backwards under the canonical-sources rule and is the inversion that produced the snapshot in the first place. **Outside it:** `050`'s scenario `a-canonical-source-is-pointed-at-not-copied` is the durable contract recording that copy as the motivating instance for the pointer rule, and it recorded it in the **present tense** — "its §Embedded artifacts section *is* a frozen copy", "the snapshot *sits* inside a code fence" — so removing the copy falsified the scenario that governs copies. Correcting it by tense cost a second reopen (050's), which is the real price of the removal and is easy to miss when pricing one. How to apply: before deleting a section, grep the corpus for its name **and** for prose describing it, then classify each hit by tense — a present-tense description of the thing you are deleting goes false, a past-tense account of why it mattered stays and is the decision record you must not destroy. Two further checks the same pass needed: per the cross-spec-signpost rule, grep for criteria asserting the section exists (none of 020's AC1-AC15 did); and a fence-aware read of the section's own extent, because `grep '^## '` finds headings that belong to the *copied* file — the same blindness that let the copy rot, applied to removing it. Deliberately **not** swept: a `review.md` naming the section as it stood at that pass, since a review record is pinned to its `reviewed-against` sha and `analyze.md` excludes `review.md` from link-adjacent drift for exactly that reason.

- **A `data-model.md` that claims "authoritative shapes" drifts from the runtime silently — check it against a record the runtime actually wrote, not against the code.** Reason: surfaced 2026-09-13 re-reviewing 020, whose data-model is the canonical record for the `review:` block and `review.md` frontmatter. Both tables had fallen behind: the block was missing `examined`, `scope` and `reviewed-digest`, and the frontmatter was missing `captured-issues`, `examined` and `scope` — six fields, all added by 022 and all live for months. 020's **own AC15** asserts that "`review.md` and the spec's `review:` block both record `examined`", so the authoritative record contradicted its own acceptance criterion, and nothing reported it: `check-artifacts` reads criteria and paths, never a schema table against a real instance. How to apply: when a pass opens a spec whose data-model declares a shape the runtime writes, open a record the runtime wrote **minutes ago** and diff the field sets by eye. Reading the struct instead is weaker — it tells you what the code can emit, not what the shipped artifact carries, and the two differ wherever a field is conditional or host-supplied. This is the schema-side twin of the enumeration rule: a table claiming to be authoritative is a claim with a source, and the source is an artifact rather than a count.

- **Point at the canonical source — never embed a copy of it.** The rule is [§drift-prevention](framework/constitution.md#drift-prevention)'s *Canonical sources*, which states both reasons and the back-edge consequence — it ships to adopters, so this entry is the contributor-side record of what a copy cost *here* rather than a second copy of the rule (which would be the rule's own failure mode). Reason: confirmed by the user 2026-09-13, who directed that the pointer pattern "must be used when available" and that it belongs with adopters, not only here. The instance: `specs/020-code-review/spec.md` §Embedded artifacts is a frozen copy of `framework/commands/review.md` running lines 242–802 of an 802-line spec — **70% of the spec**, against a live source that had grown to 894 lines. Nothing flagged it and nothing could: the snapshot sits in a code fence, so no link check, anchor resolver or audit family reads it, and a scan for the next `##` heading stops 540 lines early on a heading belonging to the copied file. A person reading the spec is the only instrument that has ever found one. How to apply: when a spec needs to record what a command, template, manifest or rule file looked like, write what the spec *delivered* and link the source; the section above governs what replacing an existing copy costs. Rule and worked example: [`a-canonical-source-is-pointed-at-not-copied`](specs/050-constitution/scenarios/a-canonical-source-is-pointed-at-not-copied.md) under 050; 020's own remediation is tracked in `specs/inbox.md`.
